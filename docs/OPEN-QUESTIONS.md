# Open Questions — implementation judgment calls

`AGENTS.md` §8.4 and `IMPLEMENTATION-PLAN.md` §0.3. This log records gaps in the
**implementation** of the locked documents, never product decisions. Ids are
never reused; answered rows are never deleted; reversing a default gets a new
row that references the old one.

The four sources stay locked (`AGENTS.md` §2.6): nothing here changes `PRD.md`,
`ARCHITECTURE.md`, `DATABASE.md` or `API.md`.

| **AG-Q13** | `API.md` §3.2 SET-2 always shows `marlaSqft` and `logoFileId` in the body, its notes only say "omitted optional text becomes `null`", and `V-19` says `marlaSqft > 0 **when present**". Which SET-2 properties are required, and what does omission mean for a non-text property? | `name` and `marlaSqft` are required: missing/blank/malformed is `400`, a well-formed value ≤ 0 is `422` (`V-19`). `address`, `phone`, `email`, `pdfTermsText` are optional; omitted, `null` or blank all store `null` (`API.md` §1.8, SET-2 notes). `logoFileId` is optional and nullable; omitted or `null` clears the logo, because `PUT` is a full replace. `marlaSqft` accepts `225`, `225.5` or `225.00` and is normalized to two decimals on write (`API.md` §1.8 wire rule). | The Zod schema, one 400/422 test per rule, and the Settings form; no table, column or DDL change. |
| **AG-Q14** | `ARCHITECTURE.md` §7.5 says "the previous logo object is soft-deleted when nothing else references it", and §7.5/`DATABASE.md` §3.11 define that reference check as a union of the three reference columns (`company.logo_file_id`, `project.master_plan_file_id`, `buyer.photo_file_id`). Does SET-2 check only its own column or the union? | The union, implemented once in `core/files.ts` (`countFileReferences`) because file lifecycle belongs to the `core` owner. It is a set of counts, not a cross-domain join. `V-14`'s kind check means a `COMPANY_LOGO` can only be referenced by `company` today, so behaviour is identical now and stays correct when SET-7/SAL-2 land. | One helper and one query; no behaviour change at v1.0. |
| **AG-Q15** | `core/errors.ts` maps each `API.md` §5 code to exactly one HTTP status, but `API.md` §1.3/§5.2 documents `VALIDATION_FAILED` as `400 / 422` (shape vs. a well-formed value that breaks a positivity rule). How is the 422 branch represented without inventing a second code? | `AppError` accepts an explicit `httpStatus: 422` option that is **only** valid for `VALIDATION_FAILED` (anything else throws), plus an `unprocessable(fields)` helper. `marlaSqft <= 0` at SET-2 uses it. No new error code, no wire-shape change. | Only `src/core/errors.ts` and its callers; the wire contract is already documented. |
| **AG-Q16** | `DESIGN.md` §13.14 draws Settings as a left sub-nav with six tabs (Company profile · PDF terms text · Expense categories · Reminder templates · Reminder channels · Marla conversion), but this PR implements only the company-owned data; the other three tabs are `IMPLEMENTATION-PLAN.md` §2.5 (Phase 5/6). What does the screen show meanwhile? | One **Company profile** form covering every company-owned field (profile, logo, terms text, marla conversion). The vertical tab shell is added by the PR that introduces the first non-company tab (expense categories, Phase 5), so no tab is ever rendered as a dead end (`DESIGN.md` §6: "never render disabled items"). | Only `settings-view.tsx` and three catalog strings; no API or table change. |
| **AG-Q17** | Neither `API.md` §1.8/§4 nor `DATABASE.md` §3.2 states maximum lengths for `name`, `address`, `phone`, `email` or `pdfTermsText` (all `text`), while `AGENTS.md` §6.2 forbids inventing a validation rule. Phase 1 already bounds its inputs (`identity/schemas.ts`: name 200, email 320, phone 32). What bounds does SET-2 use? | The same bounded-input convention as Phase 1: name 200, address 2,000, phone 32, email 320, `pdfTermsText` 20,000 characters, applied **after** trimming. Excess length is `400 VALIDATION_FAILED` with the field name. No format rule is invented for `phone` (`DATABASE.md` §3.2 says "display only"). | Three `.max()` numbers in `schemas.ts` and one 400 case; no storage change. |
| **AG-Q18** | `API.md` SET-7 says the capability is `inventory.manage`, while `ARCHITECTURE.md` §4.1 files `project` (and therefore its `master_plan_*` columns) under the **setup** module and §5.3 describes "upload/replace the master plan" as an **inventory** operation. Which module owns the SET-7 command? | The command stays in `modules/setup` because `project` is Setup's table (§2.4 rule 8: one owning module, and §2.4 rule 2 forbids a module writing another's tables), and `AGENTS.md` §4.1's module table already resolves it: setup owns "§3.2 (SET-1…11)" with "`inventory.manage` (SET-7 master plan)". The capability check is `inventory.manage`, verbatim. | Only the file the command lives in; the wire contract is unchanged. |
| **AG-Q19** | `API.md` SET-3 documents exactly one response, `200 Page<Project>`, and §5.4 scopes `COMPANY_NOT_CONFIGURED` to SET-1/SET-4. What should `GET /api/projects` answer before the singleton company exists? | `200` with an empty page (`data: []`, the requested `page`/`pageSize`, `total: 0`). A 404 would invent a response SET-3 does not list, and there is no project to return. SET-4 keeps its documented `404 COMPANY_NOT_CONFIGURED`. | One branch in `listProjects` and one test; no wire-shape change. |
| **AG-Q20** | `API.md` SET-6 lists `marlaSqft?` without saying whether an explicit `null` is legal; `DATABASE.md` §3.2 lets the column be null ("overrides `company.marla_sqft` when present") and the `Project` DTO already declares `marlaSqft: DecimalString \| null`. | An explicit `null` clears the project override back to "inherit the company value"; an **omitted** field leaves the stored value untouched. `null` and `""` are distinct from absent, so a PATCH can clear a field without rewriting it. | One branch in the command and one test; no schema change. |
| **AG-Q21** | Neither `API.md` SET-6 nor `DATABASE.md` §1.7 defines a PATCH that changes no field (only `version`). Should it bump `version`, no-op, or be rejected? | It runs the same CAS and therefore advances `version` by one, but writes **no** `project.updated` audit row because no field changed. `version` is a concurrency token, not a content hash, and the alternative — a read-then-compare shortcut — would be the exact pattern §1.7 forbids. | One condition around the audit write; no wire change. |

| **AG-Q22** | `API.md` SET-6/SET-7 each document both `404 PROJECT_NOT_FOUND` and `409 CONFLICT_STALE_WRITE`, but `DATABASE.md` §1.7's CAS is a single `UPDATE … WHERE id AND version`; zero matched rows cannot distinguish "no such project" from "someone else wrote first". How is 404 separated from 409 without reintroducing read-then-compare? | The command reads the project **inside the same transaction**, before the update, and answers `404` only when that read found nothing. The read never decides whether the write succeeds: if the row was read and the conditional `UPDATE` still matches zero rows, that is always `409` — the version check remains the sole arbiter. `project` rows are never hard-deleted (`DATABASE.md` §1.6), so a row cannot disappear between the two statements. | One read already required for the aspect/field-diff inputs; no wire change. |
| **AG-Q23** | `API.md` §1.9 derives `Project.masterPlan` from the four `project.master_plan_*` columns. `ck_project_plan_dims` (`DATABASE.md` §3.2) requires the two dimensions to be *both null or both positive*, but it does not forbid a `master_plan_file_id` with both dimensions null. What does the DTO do for such a row? | `toMasterPlanDto` throws. Every application write supplies the pair (COR-1 decodes the image, §7.3 step 5, and SET-7 stores it), so a plan id without dimensions can only come from an out-of-band `UPDATE`. Reporting `0 × 0` would fabricate a real-looking measurement; failing loudly surfaces the corrupt row instead. | One guard in `dto.ts`; no data path can reach it through the API. |
| **AG-Q24** | `IMPLEMENTATION-PLAN.md` §2.6 requires the seed to produce 1 company + 1 project with deterministic ids, but neither it nor `AGENTS.md` AG-Q5 says what a **second** `npm run db:seed` does. | Skip-if-present, never `upsert`: each row is looked up first and left untouched. An `upsert` would rewrite an Admin's edited company profile or project with demo values on a routine re-run. The project is looked up by `company_id` (the column that is unique per name), so an existing `Green City Phase 1` under any id is left alone. | One branch per row in `prisma/seed.ts`; no schema change. |
| **AG-Q25** | `AGENTS.md` §7.3 runs every integration suite against **one** `TEST_DATABASE_URL`. SET-1/SET-2 and SET-3…SET-7 both need the `company` singleton to themselves (each clears `project`/`company` to test the first-run state), but Vitest runs test files in parallel workers by default. How do two suites that both own the singleton coexist? | `fileParallelism: false` in `vitest.config.mts`: integration files share one database, so they execute one at a time and their fixtures cannot delete each other's rows. The alternative — giving each suite its own database — is not expressible through the documented single `TEST_DATABASE_URL` (`ARCHITECTURE.md` §14.3). Unit files are unaffected apart from a couple of seconds of wall time. | One config line; CI and `npm test` become deterministic instead of order-dependent. |
